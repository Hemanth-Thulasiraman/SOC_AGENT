## Part 1 — The Worked Example (read this first)

**Stale, kept for narrative intent only — do not cite specifics from this section.** This was written before Phase 6 was implemented, and several concrete details drifted during actual build: `ToolResult.status` ended up two states (`success`/`failure`) not three (`ok`/`empty`/`failed`) — a "found nothing" result is `status="success"` with an informative string, not a separate `"empty"` state; the planner emits at most one tool call per cycle, not two at once; the gate threshold is 0.7, not 0.75. The Phase 6 section below describes what was actually built and actually verified, including a real end-to-end run — treat that as authoritative over this section wherever they conflict.

Before the phase-by-phase history, here's what the finished system does with one real alert, so every decision below has a concrete anchor.

**The alert:** a phishing report reaches the system. `sender_domain` was registered recently — no threat-intel history exists for it. The user clicked the link and entered their credentials. This is deliberately the *hardest* kind of case in the design: a "disagreement" scenario where one evidence source (reputation) looks unremarkable and the other (user behavior) is damning. It's also, not coincidentally, exactly the case the Phase 5 baseline got wrong — a flat rule reading "unknown reputation" defaulted straight to benign and missed it entirely.

**Step 1 — Ingestion.** The alert arrives as a raw record: `alert_id`, `alert_type="phishing"`, `timestamp`, `source`, plus `raw_evidence` (`sender_domain`, `sender_email`, `url`, `user_id`, `click_timestamp`, `click_action="entered_credentials"`). Validation checks only the structural fields (`alert_id`, `alert_type`, `timestamp`, `source`) — all present, so it's accepted into the pipeline.

**Step 2 — State initialized.** A fresh investigation state is created: empty `evidence` list, empty `circuit_breakers` dict, `planning_count=0`, `tool_call_count=0`, `confidence_score=None`, `escalation_flag=False`, `verdict=None`, `start_timestamp=now()`.

**Step 3 — Planner, cycle 1.** The agent reasons about what a phishing alert like this needs: sender/link reputation, and the user's own click history. It emits two tool calls.

**Step 4 — Tool execution.**
- `reputation_lookup(sender_domain=...)` runs. The domain has no history — this comes back `status="empty"` (the tool ran successfully, it just found nothing), not `status="failed"`. That distinction matters: "no data" and "broken tool" must never look the same to the planner.
- `click_history_lookup(user_id=...)` runs. It finds a record: `status="ok"`, `result_summary="user entered credentials at [timestamp]"`.
- `tool_call_count` is now 2.

**Step 5 — Evidence recorded.** Both results are appended to the state's `evidence` list, each as `{tool_name, result_summary, status, timestamp}` — the same generic shape regardless of which tool produced them.

**Step 6 — Reflection.** `planning_count` increments to 1 (well under the 5–6 cap). The planner asks: is this enough to verdict? For phishing, only two evidence sources exist and both have now been checked — yes, proceed to verdict.

**Step 7 — Confidence scoring.** This is where the Phase 2 weighting decision does its job. Click history is the high-load-bearing signal (internal, never legitimately silent, and "credentials entered" is close to the most damning finding it can return) — it pushes hard toward malicious. Reputation coming back empty is *not* penalized heavily, because "no history" is the expected state for newly-registered infrastructure, not an anomaly. Net result: confidence lands around 0.68 — clearly malicious-leaning, but not overwhelming, because the corroborating signal (reputation) simply isn't available one way or the other.

**Step 8 — Verdict + gate.** `verdict="malicious"`, `confidence_score=0.68`. The confidence gate threshold (0.75) isn't met — this doesn't auto-resolve. `escalation_flag=True`. This is the load-bearing moment of the whole project: the baseline, on this exact evidence, said "benign" with total confidence and moved on. The agent, on the same evidence, correctly recognizes it doesn't have quite enough to be fully certain — and routes to a human instead of guessing wrong.

**Step 9 — Escalation.** The investigation is pushed onto the durable review queue with its full evidence trail attached — not just the verdict, but *why*: "unknown reputation (no history — not necessarily benign), user entered credentials." A SOC analyst opens it, reads the same two facts, and confirms: malicious. `human_verdict="malicious"`, `human_decided_at=now()`.

**Step 10 — Feedback + memory.** The investigation closes. A short summary is generated — *"Phishing alert, credentials entered on unknown-reputation link, escalated to analyst, confirmed malicious."* — embedded, and written to the `investigations` table alongside the structured fields. This case is now part of episodic memory: if a similar pattern shows up again, semantic search can surface it. It's also now one data point toward the escalation-precision metric — this escalation was correct (`verdict` and `human_verdict` agree), so it counts as a true positive.

**What would've been different if a tool failed:** say `reputation_lookup` timed out, was retried once, and failed again. The circuit breaker for that tool trips for the rest of *this* investigation. The result still flows into the evidence list, but as `status="failed"` rather than `"empty"` — a different signal to the planner than "we checked and found nothing." It still lowers confidence the same way an empty reputation check would, through the same single confidence mechanism — there's no separate override path that forces escalation just because a tool broke.

That's the whole system, once. Everything below is *why* it works this way.

## Part 2 — Phase-by-Phase Decisions

### Phase 1: Problem Framing

- **Persona:** in-house Tier-1 SOC analyst, mid-size company (chosen over MSSP — which would add multi-tenant complexity with no new agentic concept — and over SOC lead, which is a different problem: reviewing verdicts, not producing them).
- **Problem, with numbers:** 174 alerts/day, only ~22% need real investigation, 52% of analyst time lost to false positives.
- **Why not a rules engine or a classifier:** a rules engine is brittle to novel patterns; a classifier can predict a label but can't explain itself, gather more evidence, or correlate across sources — it performs one prediction, not an investigation.
- **Why a genuine agent:** different alert types require genuinely different, runtime-discovered evidence-gathering paths (phishing needs sender/click evidence; lateral movement needs flow/history evidence) — a fixed pipeline can't adapt to that, an agent has to reason about what's missing and decide what to check next.
- **The differentiator, sharpened later:** the project's real value is catching alerts that *look* normal by surface metrics but are actually harmful — exactly the case a threshold rule is structurally blind to, and exactly what Phase 5's baseline results ended up proving empirically.
- **Metrics locked (with real formulas):** time-to-verdict (median/p95), throughput, escalation precision (confirmed-true-positive escalations ÷ total escalations), false-negative rate on missed true positives, cost per investigation.

### Phase 2: System Design

- **Framework:** LangGraph — ReAct-style loop with bounded reflection, chosen because the evidence-gathering plan isn't knowable up front; LangGraph's interrupt/checkpoint model also gives a clean HITL pause-and-resume.
- **Loop bounds:** `planning_count` capped ~5–6 cycles, `tool_call_count` capped ~10–12, checked independently (one cycle can trigger multiple tool calls). Numbers derived from a real cost calculation: ~$0.01–0.02/cycle at current Claude pricing, targeting ≤$0.10/investigation and <2 min time-to-verdict. **Either cap breached → auto-escalate**, never auto-resolve — defaulting to "resolved" on insufficient evidence would silently produce the most dangerous failure mode (a false negative).
- **Tool resilience — circuit breaker pattern:** timeout or garbage response → retry once → still bad → trip the breaker for that tool, for the rest of *this* investigation only, log it, continue with remaining tools. Per-tool state (`{status, failure_count, last_attempt}`), not a single investigation-wide counter.
- **Tool failure does not bypass the confidence gate.** It's treated as missing evidence — lowers confidence proportional to how load-bearing that source is for this alert type — and the *same* gate decides escalate vs. auto-resolve either way. One mechanism, not two competing rules (this was explicitly debated and locked after an early draft tried to hard-override escalation on any tool failure, which would've tanked escalation precision by escalating cases the remaining evidence could resolve fine).
- **Confidence scoring is reasoned per evidence source, per alert type — never flat weights.** Worked example: for phishing, click history (internal, never legitimately silent, can be strongly damning) outweighs reputation data (external, "no history" is the *expected* state for new malicious infrastructure, not a real gap).
- **State object:** alert data, generic `evidence` list, per-tool `circuit_breakers` dict, both counters, running `confidence_score`, `escalation_flag`, `verdict`, `start_timestamp`/`verdict_timestamp` (aggregate stats like median/p95 are computed later across many runs, never stored per-investigation).
- **HITL:** one gate, one mechanism, delivered via a durable queue (not an in-memory return value) so it survives stateless requests.
- **Memory:** LangGraph state (short-term) + Postgres/pgvector (episodic — needs both SQL correlation and semantic similarity, which is why a pure vector store or pure relational store alone wouldn't work).
- **LLM provider:** Claude, chosen specifically for tool-use reliability and resistance to hallucinated confidence — a confidently wrong "benign" verdict on a real intrusion is the single most expensive failure mode this system can produce.

### Phase 3: Data Design and Ingestion

- **Hybrid dataset, justified by evidence-modality diversity, not attack-count breadth.** CICIDS2017 covers several real network-flow attacks (DDoS, brute force, botnet, port scan, infiltration), but they're all the *same kind* of evidence — three of them together wouldn't demonstrate the agent reasoning differently, just applying the same tool category with different flags tripped. Phishing (fully synthetic — no dataset covers it) is the one alert type forcing genuinely different evidence (identity/behavioral, not network-flow), which is what actually demonstrates adaptive reasoning.
- **Lateral-movement label chosen: `Infiltration`** — not because it's well-supported (it's the rarest class in CICIDS, 36 rows), but *because* it resists simple detection, which is the whole point (see the differentiator above).
- **Schema:** shared structural fields (`alert_id`, `alert_type`, `timestamp`, `source`) plus type-specific `raw_evidence` — only fields the agent's tools actually consume, not every available column (an explicit lean-vs-complete tradeoff, resolved toward lean since re-ingesting later is cheap at POC scale).
- **Validation:** reject only on missing structural fields. Missing evidence fields are never rejected — they flow through the same confidence-penalty mechanism as a failed tool call, reusing one mechanism instead of building a second rule for the same underlying situation.

### Phase 4: Data Analysis and Preprocessing

- **CICIDS reality check:** the full label distribution (`BENIGN` 2.27M, various attacks, `Infiltration` only 36) was pulled directly rather than assumed — an earlier look at a single day's file had only shown DDoS/Benign, which would've been a real mistake if not caught.
- **IP columns:** the "cleaned" ML-oriented CICIDS distribution strips source/dest IP (correctly, for training a classifier, to prevent shortcut-learning) — but this project needs IPs for SQL correlation, not classifier training, so the IP-inclusive version was used instead.
- **Synthetic Infiltration generation:** row-wise template + jitter (not independent per-field sampling), chosen specifically because independent sampling on only 36 rows risks generating physically implausible field combinations with no way to catch them. IPs get last-octet jitter, **consistent per template** (same template → same synthetic IP every time it's sampled) so the SQL correlation tool can be tested against its actual purpose: recognizing the same host acting repeatedly, not just generating maximally diverse noise.
- **Synthetic phishing generation:** a 2×2 scenario matrix (true label × whether visible evidence agrees with the truth), not a single random generator — because a dataset where "bad signal" always pairs with "malicious" is trivially separable and would never test whether the confidence weighting actually matters. ~40% true-malicious rate (above the overall 22% average, reasoned from the fact that these alerts already passed a filter or got a human flag — a pre-screened, not random, population), 50/50 agree/disagree split within each label. A hidden `true_label`, separate from the visible evidence, makes false-negative rate actually computable.
- **Episodic memory table:** one Postgres table, structured columns and a `summary_text`/`embedding` pair on the *same row* — not separate stores — so exact SQL lookups and semantic similarity search both hit one place. Embedding model: OpenAI `text-embedding-3-small` (Claude has no embeddings endpoint). Summary generated by one final LLM call after verdict, forced into a fixed sentence template so embeddings stay comparable across rows. `key_evidence` for that template is chosen *deterministically* by code (highest-weighted successful tool result for that alert type), not left to the LLM to pick — keeping "what mattered most" auditable and consistent, matching the whole project's evidence-trail philosophy.
- **ANN index deferred:** an `ivfflat` index was drafted then removed — at a few hundred rows, an approximate index has too few vectors per cluster to help, and a plain sequential scan is fast enough; revisit once real volume exists.

### Phase 5: Baseline Solution

- **Purpose:** prove the "why not a simpler solution" argument from Phase 1 empirically, not just assert it — and give the agent a real number to beat.
- **Approach:** hand-written rule scorers, deliberately built to be *correct* on easy cases (so any failure is provably structural, not the baseline being tuned weak) and to fail only where evidence needs to be fused across sources or correlated across time — capabilities a fixed rule cannot have by construction.
- **Reframed metrics:** cost, latency, and throughput are a *budget* the agent must stay inside (tied to the Phase 2 caps), not a contest — a bare `if/else` will always win those trivially, and reporting it as a loss for the agent would be misleading. **Escalation precision and false-negative rate are the real contest.**
- **Phishing baseline result:** 0.000 escalation precision, 0.501 false-negative rate. Perfect on the "agree" scenario cells, complete failure on both "disagreement" cells — proving the rule fails exactly where fusing two evidence sources is required, not randomly.
- **Lateral-movement baseline result:** 0.753 escalation precision, 0.218 false-negative rate — notably stronger than phishing's. **Caveat recorded explicitly:** this may partly reflect that all malicious rows trace back to only 36 real templates (a tight cluster a single threshold can catch), not a general claim that rule-based detection works better on network attacks than phishing. The rule's blind spot — quiet, low-volume "completed-looking" connections — is exactly what SQL correlation (repeat contact from the same host over time) is built to catch, and exactly what the baseline structurally cannot see one flow at a time.

### Phase 6: Tool Registry, Real Tools, and the Agent Graph (done)

**6a — Tool registry.** `ToolResult` has two states in the actual implementation, `success`/`failure`, with `evidence: str | None` — always a real string (possibly an uninformative-but-legitimate one, like "no reputation history found") on success, always `None` on failure. `ToolRegistry.dispatch()` is a pure function over `circuit_breakers` state (state in, state out), never a mutated global — matches LangGraph's model and stays trivially testable. Retry-then-trip logic lives in one place, not duplicated per tool. The breaker opens the *first* time `dispatch()` sees a failure, not the second — the internal retry already represents two raw attempts, so counting a second `dispatch()`-level failure as the trigger would double-count. `tool_call_count` enforcement stays the calling graph node's job, not the registry's, matching the same separation as the two independent Phase 2 caps.

**6b — Four tools, all keyed by `alert_id`, never by a "natural" field.** This wasn't the first instinct for any of them — each one was caught by checking, not assuming:
- `click_history_lookup`: keyed by `alert_id`, not `user_id` — the same user can legitimately recur across separate investigations (a user phished twice), so a `user_id`-keyed lookup risks silently returning a *different* alert's click outcome. A missing record is treated as anomalous (internal log, should always exist) and raises — unlike a missing reputation result, which is an expected, legitimate empty state.
- `reputation_lookup`: keyed by `alert_id`, not `sender_domain` — verified empirically, not assumed: at n=2000 synthetic phishing rows, 205 domains repeat across multiple alerts with a *different* `reputation_signal` assigned each time. A domain-keyed fixture would have silently returned one alert's signal for a different alert.
- `ip_reputation_lookup`: same discipline, plus a new mock `ip_reputation_signal` field (`assign_ip_reputation_signal`) added to mirror phishing's agree/disagree scenario design, since lateral movement had no equivalent field. Verified against a live collision: `192.168.10.12` is shared by a synthetic malicious template *and* 119 real benign flows — every alert still resolved to its own correct signal.
- `sql_correlation`: the tool built specifically to fix the baseline's proven blind spot (the "quiet flow" 95/436 false negatives). Required fixing a real gap first — lateral-movement alerts had no `timestamp` field at all. Then a deliberate generation choice: repeat occurrences of the same host are spaced **1–14 days apart**, not minutes/hours, so a prior investigation has time to fully resolve and get written back before the next occurrence of that host is even alerted — otherwise the tool has nothing to find regardless of query correctness. **Locked requirement, recorded in `docs/05-baseline.md`: Phase 8's eval harness must process alerts in timestamp order**, or this guarantee is meaningless. The correlation window (28 days) is derived by import from the generator's own max-gap constant, not a coincidentally-matching duplicate.
- All four tools gained explicit `None`-guards on their non-keyed arguments (`sender_domain`, `dest_ip`, `source_ip`, `alert_timestamp`) after realizing these fields aren't part of any lookup key — only the display string — so a missing value would otherwise produce a plausible-looking but false `success` (e.g. `"domain None has known-malicious reputation"`) instead of a real, catchable failure.

**6c — The planner/reflect graph.** Two separate LLM nodes, not one — `planner` decides what to check next, `reflect` decides continue-vs-verdict — because merging them would reproduce the "one thing doing two unrelated jobs" pattern rejected everywhere else in this design. Cap enforcement lives entirely on the graph's edges (`route_after_reflect`), never inside the reasoning nodes — same separation as the registry not knowing about `tool_call_count`. **Locked: neither prompt is ever told `planning_count`, `tool_call_count`, or either cap** — a model that knows it's on "cycle 6 of 6" has a reason to say "done" unrelated to whether the evidence is actually sufficient, which would silently corrupt `confidence_score` as an honest signal. Tool selection uses native structured tool-use, not free-text parsing — and every tool schema exposes **zero argument fields**, since every real argument (alert_id, sender_domain, dest_ip...) is already a fact in state, bound deterministically by `build_tool_kwargs` — this doesn't just reduce parameter-hallucination risk, it removes the failure mode entirely. When `planner` declines to call a tool, routing skips `tool_execution` and goes straight to `reflect`; if `reflect` still wants to continue with no tools left, that gets the *identical* treatment as a cap breach — forced escalation — because "ran out of things to try" and "the evidence was actually sufficient" are different claims, and only the second one should ever justify voluntarily stopping. Confidence scoring and the final auto-resolve/escalate gate are both deterministic code, not LLM calls, applying the Phase 2 per-source weighting.

**Verified end-to-end, twice — only the second time counts.** A first pass used a scripted stub in place of an LLM to prove the scaffolding (routing, caps, both forced-escalation paths) — genuinely useful, but it can't validate reasoning because it isn't doing any. The first real-model pass (OpenAI GPT-4o — no usable Anthropic credit balance at the time) appeared to fail the exact case the whole project exists to catch, but the actual bug was upstream: `raw_evidence` had been built from `row.to_dict()`, dumping tool-gated fields (`click_action`, `reputation_signal`) *and the hidden ground-truth `true_label`* straight into the prompt. The model's behavior was rational given a leaked prompt, not a reasoning failure — caught by noticing the result was suspiciously efficient (skipped a now-redundant tool call) rather than assuming a clean pass. Fixed at the actual boundary, not just the call site that happened to trigger it: `new_investigation_state` now enforces an explicit per-alert-type allow-list and raises if anything tool-gated or eval-only is passed in, so the same leak can't recur silently in Phase 8's eval harness or any other future caller. Re-verified with the leak closed: on phishing's `malicious_disagree` case (the exact cell the Phase 5 baseline missed 100% of the time), the model chose `click_history_lookup` on its own, reasoned to `verdict=malicious` at confidence 1.0, correctly auto-resolved. On the lateral-movement repeat-offender case, both tools were called, `sql_correlation` surfaced 2 prior malicious verdicts, `verdict=malicious` at confidence 0.6 — correct, and correctly escalated rather than blindly auto-resolved. **What this does and doesn't prove:** the reasoning layer is genuinely demonstrated end-to-end, on a clean non-leaking input, against a real model, on the two cases specifically designed to be hard. It is not a systematic evaluation — two hand-picked cases are an existence proof, not a reliability claim. That gap is exactly what Phase 8 exists to close.

### Phase 7: Real Postgres/pgvector Integration (done)

**The real `investigations` table.** Created via `sql/001_create_investigations.sql` (the exact Phase 4 SQL, no `ivfflat` index, as deferred), run against a live `pgvector/pgvector:pg16` container and verified column-by-column with `\d investigations` against the Phase 4 design before any code touched it — all 23 columns, all four check constraints, `alert_id` uniqueness, `embedding vector(1536)`, exact match.

**Environment problem caught before it wasted anyone's time:** a native/Homebrew Postgres was already bound to port 5432 on the dev machine, silently intercepting connections meant for the container (`FATAL: role "postgres" does not exist` — not a container bug, a different Postgres entirely). Container recreated on **port 5433** instead of fighting the native install. Written down in `.env.example` and the README's local-setup section specifically so this doesn't cost a future 10-minute debugging session — the whole point of catching it once is not having to catch it again.

**`sql_correlation` rewritten from the Phase 6b DataFrame stand-in to a real `psycopg` connection** — same matching logic, same window, same success-even-when-empty rule, only the data source changed. Filters on `verdict_timestamp IS NOT NULL` (an in-flight investigation has a `NULL` `verdict_timestamp`, so it's structurally invisible to its own query before the explicit `alert_id != alert_id` exclusion even applies — a side effect of the earlier verdict-vs-start-timestamp reasoning, not something separately engineered). The `alert_id` exclusion is kept anyway as cheap insurance against a race (e.g. a retry writing a partial row), even though normal operation doesn't need it. Two real bugs only surfaced by testing against the live table, not by trusting the query: the port conflict above, and Postgres's `INET` type rendering `::text` as `'10.9.9.1/32'` (includes the netmask) rather than a bare address — silently broke the exact-host-pair-match comparison until replaced with `host()`. Verified with real inserted rows covering a full-pair match, a single-field-only match, an out-of-window match (correctly excluded), and a genuinely new host (correctly empty) — not just "the query ran."

**`feedback_memory_node` now does the real write-back Phase 4 designed.** `key_evidence` selection is deterministic code reusing `confidence.py`'s existing per-alert-type weights (not a second, unauditable LLM judgment) — same discipline as the original Phase 4 design intent. Summary generated via the exact fixed template (one LLM call, any provider), embedded via OpenAI `text-embedding-3-small` **always**, regardless of which provider is driving planner/reflect reasoning — Claude has no embeddings endpoint, so a second provider is structurally required either way. Vector-type adaptation via `pgvector.psycopg.register_vector`. Verified against the real database: generated summaries matched the exact template format for both alert types, and the embedding was independently confirmed as a real 1536-dimension `vector` column value (`vector_dims()` on a live row), not just "the insert didn't error."

**`true_label` kept structurally outside agent-visible state.** Rather than threading eval-only ground truth through `state`/`raw_evidence` (the exact path that caused the Phase 6 leak), it's supplied to `feedback_memory_node` directly via a `true_label_lookup` side-channel owned by the calling harness. This doesn't just avoid a repeat of that mistake once — it removes the code path by which it could happen again, which is the right response to having found it the first time.

**Semantic-similarity search (`ORDER BY embedding <=> query_vector`) deliberately left unexercised.** `sql_correlation` was scoped to exact-match only because that's what's tested and what actually fixed the Phase 5 blind spot; nothing in the current design needs semantic search to function. Building a code path with no consumer yet would be speculative — it's recorded on the V2 list below instead.
